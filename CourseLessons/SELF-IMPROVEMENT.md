# SELF-IMPROVEMENT — mistakes, findings, and how agents learn from each other

The pipeline is self-improving because every agent leaves behind what it
learned. This is mandatory, not optional: **an agent that hides a mistake
hurts every successor.**

## 1. The findings ledger (`<course>/findings.jsonl`)

Append-only, one JSON object per line:

```json
{
  "id": "f-0007",
  "date": "2026-10-22",
  "agent": "session web-… trace …",
  "type": "content-error",
  "lesson": "u1-c01-states-of-matter",
  "section": "s02",
  "severity": "error",
  "what": "Prose said particles 'expand' when heated (solid lattice).",
  "why": "Misconception: spacing changes, particle size does not. Source chunk actually correct; error introduced in my rewrite.",
  "fix": "Rewrote to 'the spaces between particles increase'.",
  "root_cause": "Prompt 'lesson-prose@1.0.0' encourages paraphrase without a physics guardrail.",
  "system_change": "lesson-prose@1.1.0 adds 'never alter physical claims' rule",
  "status": "closed"
}
```

**Types:** `content-error` | `ocr-artifact` | `spec-mismatch` |
`ms-vocab-better` (found a better mark-scheme line) | `lint-false-positive` |
`lint-gap` (lint should have caught this) | `feature-gap` | `process` |
`duplicate-work` (two agents built the same thing — tracker/receipt failure).

## 2. Root-cause-twice law

The first occurrence: fix the content, file the finding.
The **second** occurrence of the same root cause: fixing the content is not
enough — the agent MUST also change the system (prompt edit, lint rule, spec
clarification, or playbook change) and reference that change in the finding.
A root cause appearing a third time means the system change failed: escalate
to the operator in the receipt.

## 3. Reading the ledger before you write

Before authoring a lesson: read the course `findings.jsonl`. Ten minutes
there saves an hour of repeating a predecessor's mistake. `lessonctl.py
report` prints the top recurring root causes so you can see the current
failure modes at a glance.

## 4. Retros (per phase)

At the end of each phase batch (e.g. "Unit 1 lessons complete"), the closing
agent appends a retro to `<course>/qa/retros.jsonl`: what went well, what
recurring findings emerged, which prompts/lints changed, metrics delta. The
next phase starts by reading the last retro.

## 5. Metrics (regenerated by `lessonctl.py report`)

| Metric | Meaning | Target (pilot) |
|---|---|---|
| sections_done / sections_total | lesson progress | 100% per published lesson |
| box_coverage | sections with required boxes (V5) | ≥95% |
| ms_line_coverage | exam-hint boxes carrying ≥1 `ms_accepts` | ≥90% |
| finding_rate | findings per 10 sections written | trending DOWN over phases |
| lint_pass_first_try | % sections passing lint first attempt | trending UP |
| duplicate_work_incidents | should be 0; >0 means tracker discipline failed | 0 |

## 6. Prompt versioning tie-in

Every finding that names a prompt in `root_cause` results in a prompt version
bump (`prompts/` registry) before the finding is `closed`. This is how the
writing itself gets better over time instead of agents patching the same hole
forever.
