# BUILD-PLAYBOOK — how Lessons get built

## 1. The pipeline in one picture

```text
CORPUS SIDE (this folder, syllabai-resources)                PLATFORM SIDE (syllabai-v2)
L0 section map      section_map.py — chunks_v3 × spine →     contracts/books-lesson.ts (lessonPackV1)
                    section spine per chapter                (contracts-first law)
L1 lesson authoring lesson.yaml + sections/*.md + boxes +
                    glossary.yaml   (S0–S3 below)
L2 lint             lessonctl.py lint  (VALIDATION.md law) → same law mirrored in CI lint pack
L3 handoff          pack → lessonPackV1 JSON emit;           SUGGESTED lands via PR;
                    receipts attached                        operator VALIDATE flip → served
L4 serve            —                                        hub Lesson renderer (Rail/Lesson tab);
                                                             cross-links DERIVED from spec joins
```

Binaries never enter this folder as copies of platform data; lessons reference
the parse of record by provenance. Text lives here; rendering lives there.

## 2. Stage flow (per lesson)

| Stage | Name | Output | Gate |
|---|---|---|---|
| **S0** | Map | `lesson.yaml` skeleton: section spine from `section_map.py`, block refs, feature checklist | G1: spine sanity (ids, pages monotonic, specRefs subset) |
| **S1** | Prose | `sections/sNN-*.md`: provenance-checked prose + page anchors | G2: lint (schema, banned phrases, OCR artifacts) |
| **S2** | Boxes | additive boxes per FEATURE-SPEC §2 coverage rules + glossary chips | G2 + coverage audit (DoD §5) |
| **S3** | Practice | quick checks wired to specRefs; worked examples; lesson-closing layer content | G3: checkRefs resolve in bank; MS lines verbatim-true |
| **S4** | Handoff | emit lessonPackV1 JSON + `qa/receipt.yaml` + tracker transaction | G4: receipt complete; `tracker_check.py` exits 0 (V10 rollup); operator review queue |

Small units of work are encouraged: one stage, or even one section, per agent
session. The tracker and receipts exist precisely so work can be picked up
mid-stream by a different agent.

## 3. Resume protocol (continue a partially built lesson)

1. `python3 scripts/lessonctl.py resume <lesson-dir>` — prints a **WORK-ORDER**:
   - current stage + receipts present;
   - sections done/missing (with which boxes each still needs);
   - lint status and the exact failing rules;
   - the next smallest useful unit of work.
2. Do exactly what the work order says. Re-run `resume` after each unit.
3. Never overwrite a section another agent completed — extend boxes or open a
   finding if its content is wrong.

## 4. Start-from-scratch protocol

1. Confirm the tracker shows no folder for the chapter.
2. `python3 scripts/lessonctl.py scaffold --course <course> --chapter u1:cNN`
   — emits `lesson.yaml` (S0) + empty section files with front-matter.
3. Work S1 → S4. Lint after every section, not at the end.

## 5. Receipts (`qa/receipt.yaml`)

```yaml
stage: S2
date: "2026-10-22"
agent: "<agent id / session trace>"
prompt_version: "lesson-prose@1.0.0"     # from prompts/ registry
lint: "PASS"                              # or failing rule ids
trace_id: "<gateway trace if available>"
summary: "S2 boxes for sections s01–s06; 3 findings filed"
```

A stage without a receipt is not done (START-HERE law 8).

## 6. Prompt registry (`prompts/`)

Every prompt used for generated content is versioned here
(`lesson-prose@X.Y.Z`, `lesson-boxes@X.Y.Z`, …). Receipts pin the version. A
prompt change that alters output style is a minor bump + one-line changelog;
a change that alters content rules is a major bump + a findings entry.

## 7. Tracker discipline

`tracker.yaml` is machine state; `TRACKER.md` is its human projection,
regenerated by `lessonctl.py report`. All transitions go through
`lessonctl.py tracker --set … --receipt qa/receipt.yaml` so the audit trail
is one file. Never hand-edit `tracker.yaml` while an agent session is live.

### The flip-tx checklist (what ONE tracker transaction touches)

A flip / tracker transaction is complete only when the SAME commit carries
ALL of:

1. the per-lesson row in `TRACKER.md` (status cell → `pack PUBLISHED`/`pack DRAFT`);
2. the per-lesson entry in `tracker.yaml` (`pack_status`, `last_receipt`,
   `last_agent`, `updated_at`);
3. the **phase rollup** — when the flip publishes the phase's last
   unpublished pack: `phases.<unit>.status` → `complete` in `tracker.yaml`
   AND the Unit-N row headline + tail closed in `TRACKER.md`;
4. the `TRACKER.md` header stamp (regeneration note, receipt-anchored).

Then `python3 scripts/tracker_check.py` must exit 0 before push (V10; it
re-derives the phase rollup, the pack JSON truth, and both row families).

**Why this checklist exists (drift instances of record):** c25 left the
Unit-4 row headline at 3/8 while 4 packs were published (repaired in-lane by
c27, 3/8→5/8, disclosed); c29 flip `a2005a16` updated row 29 + the c29 pack
entry but left row 66 at "UNIT-4 LANES 6/8 … next lane u4:c29" and
`phases.unit-4: in-progress` while its own message declared "8/8 — the
Unit-4 roster complete" (repaired in `295fb5b6`, which also closed the
same-class stale `phases.unit-2` and rows 63/64 "open" headlines). Three
occurrences = the prose-only rule failed; the system change is this
checklist + the V10 gate (`tracker_check.py`) + finding `f-0035`.
