## Paradigms

### What is a programming paradigm?

- A programming paradigm is a **style or approach to programming** that influences:

  - How programs are **written**
  - How problems are** broken down**
  - How solutions are **structured**
- **Different **paradigms are suited to **different **types of problems and systems

#### Programming paradigms comparison table

| **Paradigm** | **Description** | **Key characteristics** | **Examples** |
|---|---|---|---|
| **Low-level** | Closest to machine code, using **mnemonics **to directly control hardware | - Direct memory access<br>- Register manipulation<br>- Hardware-specific instructions | x86 Assembly, ARM Assembly |
| **Imperative (Procedural)** | Tells the computer **how** to perform tasks using sequences of commands | - Step-by-step instructions<br>- Use of loops, conditions<br>-Procedures/functions | C, Pascal, Python (procedural) |
| **Object-Oriented** | Models real-world entities using **objects** that combine data and behaviour | - Classes and objects<br>- Encapsulation, inheritance, polymorphism<br>- Modularity | Java, C++, Python (OOP) |
| **Declarative** | Describes **what** should be done, not how to do it | - Rule-based or logic-based<br>- No explicit control flow<br>- Focus on outcomes/results | SQL, Prolog, Haskell |

#### Strengths and weaknesses of programming paradigms

| **Paradigm** | **Strengths** | **Weaknesses** |
|---|---|---|
| **Procedural** | - Clear flow of control (top to bottom)<br>- Efficient for simple tasks<br>- Easy to implement algorithms<br>- Strong step-by-step logic | - Becomes hard to manage in large programs<br>- Poor modularity can lead to redundancy<br>- Not ideal for complex state-based systems |
| **Object-Oriented** | - Enhances modularity with encapsulation<br>- Real-world modelling via objects<br>- Code reuse through inheritance<br>- Polymorphism for flexible interfaces | - Can become overly complex<br>- Slower due to object overhead<br>- Misuse leads to bloated hierarchies<br>- Not ideal for every problem |
| **Low-Level (Assembly)** | - Complete control over hardware<br>- Highly optimised for performance<br>- Transparent view of machine operations | - Steep learning curve<br>- Hardware-specific, not portable<br>- Manual memory management is error-prone<br>- Difficult to debug/scale |
| **Declarative** | - Focuses on the result rather than the process<br>- Concise and expressive<br>- Suitable for complex logic or rule-based problems (e.g. AI, SQL queries) | - Harder to learn for beginners<br>- Less control over program flow<br>- Not suited for all types of problems<br>- Debugging can be challenging due to abstraction |
