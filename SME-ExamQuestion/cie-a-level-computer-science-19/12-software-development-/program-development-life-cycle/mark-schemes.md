# Mark Schemes — Program Development Life cycle
**12. Software Development** · Cambridge (CIE) A-LEVEL computer-science (9618)


## Exam Questions (16 questions)


### Q1
Meeting the fixed date: modules are developed in parallel, so several parts of the ticket program are built at the same time and the total development time is shorter. **[1]** Small releases are made, each adding functionality, so a version that can sell tickets exists on the fixed date even if some features are not finished. **[1]**

The problem: the RAD life cycle needs the client to be involved during all stages of development. **[1]** If the organisers are not available, the prototypes are not reviewed on time, so the team keeps building on requirements that have not been confirmed and that work may have to be done again. **[1]**

**[4 marks]**

> **[mark-scheme]**
> Max 2 marks for the fixed date, one mark per principle applied, from:
> 
> **1 mark** for modules being developed in parallel, so several parts of the program are built at the same time and the elapsed development time is shorter
> 
> **1 mark** for small incremental releases, so a usable ticket program exists on the fixed date even if some functionality is still missing
> 
> **1 mark** for minimal detailed planning, so work on the program starts sooner
> 
> **1 mark** for prototypes being produced early, so problems are found and corrected well before the date
> 
> Max 2 marks for the problem:
> 
> **1 mark** for identifying that the RAD life cycle requires the client to be involved during all stages of development
> 
> **1 mark** for a consequence: prototypes are not reviewed on time, so the team continues to work from requirements that have not been confirmed // work has to be repeated later // the release is delayed
> 
> Max 4 marks in total
> 
> Accept "the development process is flexible" or "RAD is used for time-critical development" as a principle when it is linked to meeting the date, for example requirements can be changed without restarting the project. Do not accept a principle stated with no link to the deadline.

> **[exam-tip]**
> This model asks as much of the client as it does of the developers, and that is what the second half of the question is testing. Students revise the benefits of RAD and forget that they depend on the client turning up. Whenever a question tells you something about how available a client is, expect that detail to carry marks.

### Q2
Benefit 1: several modules of the program can be developed at the same time, so the program is finished sooner than it would be if every stage were completed in turn. **[1]**

Benefit 2: a prototype is produced at an early stage, so the charity can review it and ask for changes to the requirements while there is still time to make them. **[1]**

Drawback: the cost and the time needed to complete the project are difficult to estimate, because the requirements are not fixed at the start. **[1]**

**[3 marks]**

> **[mark-scheme]**
> **1 mark** each for two benefits (max 2), from:
> 
> quicker development is possible, because several modules can be worked on at the same time
> 
> a prototype is produced at an early stage in the process
> 
> requirements are easier to change // usable modules are delivered sooner
> 
> early review is possible // the developer and the charity work closely together
> 
> **1 mark** for one drawback, from:
> 
> it is difficult to estimate the cost or the time to complete the project
> 
> documentation is often omitted
> 
> the charity must be available throughout the life cycle, and it is too easy for a client to keep changing its mind
> 
> Do not accept a benefit that is not a comparison, such as "it uses stages", because the waterfall life cycle uses stages too.

> **[exam-tip]**
> Read the tariff split carefully: two benefits and one drawback means three separate points, and a fourth benefit cannot replace the missing drawback. The single most common wasted answer is to repeat the same benefit in two forms, for example "it is quicker" and "it saves time". Give one benefit about speed and one about the client.

### Q3
Modules of the program are developed in parallel, as prototypes. **[1]**

Small releases are made during development, each one adding more functionality to the program. **[1]**

**[2 marks]**

> **[mark-scheme]**
> **Any two from:**
> 
> - modules are developed in parallel // modules are developed as prototypes
> - minimal or no detailed planning is carried out // the requirements are allowed to change during development
> - the development process is flexible
> - small incremental releases are made, each one adding functionality
> - the client is involved during all stages of development
> - it is used for time critical development
> 
> **[2 marks]**
> 
> Do not accept "it is rapid" or "it is fast", which repeat the name of the model instead of giving a principle of it.

> **[exam-tip]**
> The name of this model tells you its aim, not how it works, so an answer built out of the word "rapid" earns nothing. Learn the principles as a short list and give two that are clearly different from each other: "it is flexible" and "requirements can change" are close enough that an examiner may read them as one point.

### Q4
Problem 1: the number of repetitions the project will need is not known when it starts, because the requirements are not fixed at that point. **[1]** After seeing each version the hotel chain could ask for changes and new features, and every change added more work, so the cost and the completion date could not be estimated accurately at the start. **[1]**

Problem 2: this life cycle carries out little detailed planning at the start and documentation is often left out. **[1]** The design changed with every repetition, so any document written for an earlier version would have been out of date, and the team's effort went into producing working software rather than written records. **[1]**

**[4 marks]**

> **[mark-scheme]**
> Max 2 marks for Problem 1, one mark per point:
> 
> **1 mark** for the number of repetitions, or the final set of requirements, not being known when the project starts
> 
> **1 mark** for the client being able to ask for changes or new features after seeing each version, with each change adding work to the project
> 
> **1 mark** for the conclusion that the cost and the time to complete the project are therefore difficult to estimate
> 
> Max 2 marks for Problem 2, one mark per point:
> 
> **1 mark** for minimal or no detailed planning being carried out in this life cycle // documentation often being omitted
> 
> **1 mark** for the design changing with each repetition, so a document written for an earlier version is out of date
> 
> **1 mark** for effort being directed at producing working software rather than at written records
> 
> Max 4 marks in total
> 
> Do not accept "the developers were disorganised" or "the client was difficult". The question asks for a cause that comes from the life cycle itself, not from the people.

> **[exam-tip]**
> Both of these are drawbacks of the iterative life cycle, and both follow from the same feature: the requirements are deliberately left open so that they can change. Students often write that the team should simply have estimated better or written more documents. That misses the point being examined, which is that the model itself makes estimating and documenting harder.

### Q5
In the waterfall life cycle every stage must be completed before the next one begins, so there is no working software until late in the life cycle. **[1]**

In an iterative life cycle the stages are repeated, and each repetition produces a working version of the program. **[1]**

The first version does not have to contain every feature, because later repetitions add functionality to it, so Company B could release its program before the program was complete. **[1]**

**[3 marks]**

> **[mark-scheme]**
> **1 mark** for the waterfall life cycle producing no working software until late in the life cycle, because each stage must be completed before the next begins
> 
> **1 mark** for the stages being repeated in an iterative life cycle, with each repetition producing a working version of the program
> 
> **1 mark** for a release being possible before the program is complete, because later repetitions add functionality to the version already released
> 
> **1 mark** for feedback from the customers using the early version being available to Company B, so early review shapes the next repetition
> 
> Max 3 marks
> 
> Do not accept "an iterative life cycle is faster", which restates the outcome given in the question instead of explaining it.

> **[exam-tip]**
> Questions like this give you the outcome and ask for the mechanism, so an answer that repeats the outcome scores nothing. Two of the three marks here are for saying what each life cycle has produced at the six month point. Compare what exists, not how good each model is.

### Q6
Name: the iterative life cycle. **[1]**

Reason: the stages of the life cycle are repeated, so a working version of the program is produced early and the changes the school asks for after using it can be included in the next version. **[1]**

**[2 marks]**

> **[mark-scheme]**
> **1 mark** for the name: Iterative
> 
> Accept: Rapid Application Development // RAD
> 
> **1 mark** for one reason, from:
> 
> the stages are repeated, so a working version is available early // small releases are made, each one adding functionality to the last
> 
> the requirements are allowed to change during development
> 
> the client is involved throughout development and their feedback decides what is built next
> 
> Accept "development is quicker // a working version is available sooner" as the reason. Do not accept a reason that is true of every life cycle, such as "it splits the work into stages".

> **[exam-tip]**
> The reason mark is lost far more often than the name mark. A reason such as "it is more modern" or "it is organised" would be just as true of the waterfall life cycle, so it earns nothing. Point at something this model does that the waterfall life cycle does not: repeat the stages, release early, and accept changed requirements.

### Q7
Program A. **[1]**

All of the requirements for Program A are known before development starts, because the safety rules are fixed by law and are published in full, so each stage can be completed before the next one begins. **[1]**

The waterfall life cycle produces a written document at the end of each stage, including the design document that the inspector must check the finished program against. **[1]**

Program B is a poor fit because the transport authority does not yet know what the app must do, and the waterfall life cycle is slow and difficult to change once the requirements have been agreed. **[1]**

**[4 marks]**

> **[mark-scheme]**
> **1 mark** for identifying Program A
> 
> Max 3 marks for justification, one mark per point:
> 
> **1 mark** for the requirements of Program A being known and fixed before development starts, so each stage can be completed before the next begins
> 
> **1 mark** for the clear deliverables produced at the end of each stage of the waterfall life cycle, in particular the design document the inspector needs // the project is easier to manage, plan and cost
> 
> **1 mark** for the requirements of Program B being likely to change, and the waterfall life cycle being difficult or slow to cope with changes to the requirements
> 
> **1 mark** for the waterfall life cycle producing no working software until late in the life cycle, so Program B would not have a usable first version within two months
> 
> Accept a justification that names the relevant stage, for example "the analysis stage can be finished completely because nothing is left to decide".
> 
> Do not accept an answer that gives no reason connected to the two programs, such as "Program A is more important" or "Program A is harder".
> 
> No marks for the justification if Program B is identified.

> **[exam-tip]**
> The command word is justify, and the question asks you to refer to both programs. A common answer lists what the waterfall life cycle is like in general and never mentions the trains or the app. Half of the justification marks here sit on Program B: say what the app needs and why the waterfall life cycle cannot give it.

### Q8
The team must return to the analysis stage and record the new requirement in the requirements specification. **[1]**

The team must then return to the design stage and change the design, for example by adding a new field to the record that stores each product and amending any algorithm that uses that record. **[1]**

The coding stage and the testing stage must then be carried out again for every part of the program that the change affects. **[1]**

**[3 marks]**

> **[mark-scheme]**
> **1 mark** for returning to the analysis stage // amending the requirements specification to include the new requirement
> 
> **1 mark** for returning to the design stage // changing the design, for example the data structure, the identifier table or an algorithm
> 
> **1 mark** for repeating the coding stage and then the testing stage for the affected parts of the program
> 
> **1 mark** for stating that the stages must again be completed in order, so work already finished in a later stage may have to be done again
> 
> Max 3 marks
> 
> Accept named design documents such as a structure chart, a flowchart or an identifier table in place of "the design".
> 
> Accept "requirements document" in place of "requirements specification".
> 
> Do not accept "the team adds the extra code and carries on". In the waterfall model a change cannot be made in a later stage without first changing the stages it depends on.

> **[exam-tip]**
> The common error is to answer as though the change costs one line of code. The question is testing the rule that makes the waterfall model what it is: every stage takes its input from the stage above, so a change in an early stage forces every later stage to be repeated. Work down the stages in order in your answer and you will pick up the marks in sequence.

### Q9
Downward arrows: the work produced by one stage is passed on and used as the input to the next stage. **[1]**

Upward arrows: more work is needed at an earlier stage before the current stage can be completed, so the team returns to that earlier stage. **[1]**

**[2 marks]**

> **[mark-scheme]**
> **1 mark** for the downward arrows: the result produced by one stage is passed to the next stage // the next stage uses the documents or code produced by the stage above it
> 
> **1 mark** for the upward arrows: more work is required at a previous stage in order to complete the current stage // the team returns to an earlier stage to correct or add to the work done there
> 
> Do not accept "the project moves forwards" or "the project goes backwards" on their own. Neither answer says what is passed between the stages, nor why the team would return to an earlier one.

> **[exam-tip]**
> Most students who lose marks here write about the direction of travel and stop. The mark is for what travels along the arrow: finished work going down, and a need for rework going up. Say what the next stage receives, and say why a team would ever go back up.

### Q10
The requirements specification produced by the analysis stage will be incomplete, **[1]** so the design and the code may solve a different problem from the one the transport company actually has. **[1]**

The testing stage has no complete statement of requirements to test the program against, **[1]** so faults reach the user and a large amount of maintenance is then needed to correct them. **[1]**

**[4 marks]**

> **[mark-scheme]**
> **Any two problems from:** one mark for the problem and one mark for the linked effect on a later stage.
> 
> - The requirements specification is incomplete or wrong, so the design and the coding are based on the wrong requirements and the finished program does not do what the transport company asked for
> - The transport company has not agreed what the program must do, so it asks for changes during the coding stage and work that is already complete has to be done again
> - There is no complete list of requirements, so the testing stage cannot confirm that the program meets them and faults are not detected
> - The size of the problem is not understood, so the time and the cost of the later stages cannot be estimated and the project falls further behind
> - Faults caused by the missing requirements are found only after release, so more maintenance is needed and correcting a fault at that point costs more than correcting it during analysis
> 
> **[4 marks]**
> 
> Accept the problem and its effect given in either order.
> 
> Do not accept "the program will not work" or "the program will contain errors" on its own, with no named later stage and no explanation of why that stage is affected.

> **[exam-tip]**
> An explain question on the life cycle needs two linked ideas, not one. Name the later stage that suffers, then say why it suffers. "The program will be wrong" names no stage and earns nothing.
> 
> Remember what the analysis stage hands on: a requirements specification. Every later stage reads that document, so a thin analysis weakens the design, the coding, the testing and the maintenance in turn.

### Q11
The data structures the module will use, recorded in an identifier table. **[1]**

The layout and the content of the reminder message that the customer receives. **[1]**

The programming language and the development environment that will be used to write the module. **[1]**

**[3 marks]**

> **[mark-scheme]**
> **Any three from:**
> 
> - The data structures to be used // an identifier table // a data dictionary
> - The validation rules to be applied to the data
> - A diagram that documents the module, for example a structure chart, a state-transition diagram or a data-flow diagram
> - The user interface // the layout and the content of the reminder message
> - The test plan // the test data to be used and the expected results
> - The programming language and the development environment to be used
> - Any library routines or existing modules that will be reused
> 
> **[3 marks]**
> 
> Accept the name of the design document instead of the item itself, for example "an identifier table" for the data structures.
> 
> Do not accept "the algorithms" or "the pseudocode for the module". The question states that these are already being designed and asks for three other items.
> 
> Do not accept "the program code", which is produced in the coding stage, or "the results of the tests", which are produced in the testing stage.

> **[exam-tip]**
> Students lose marks here by naming work that belongs to a later stage. The design stage decides the test plan and the test data; it does not run the tests. It chooses the programming language; it does not write the code.
> 
> A useful check: everything produced in the design stage is a decision or a document about how the program will work, written before any code exists.

### Q12
The project is easier to plan and manage, because each stage can be scheduled and costed separately. **[1]**

**[1 mark]**

> **[mark-scheme]**
> **Any one from:**
> 
> - The project is easier to plan / manage / schedule
> - The time and the cost of the work are easier to estimate and control
> - A clear deliverable is produced at the end of each stage, so progress can be checked before the next stage starts
> 
> **[1 mark]**
> 
> Accept an answer phrased around one stage having to be completed, and its output approved, before the next stage begins.
> 
> Do not accept "it is faster" or "it is cheaper" on its own. The benefit must say what dividing the work into stages lets the team do.

> **[exam-tip]**
> The commonest wrong answer here describes what one stage does, for example "you can test the program". That is a benefit of testing, not a benefit of splitting the work into stages. Say what the team gains: it can plan, cost and check the work one stage at a time.
> 
> Read the question carefully. This asks about using a development life cycle at all. It is not asking you to compare waterfall, iterative and RAD, and a comparison of those models earns nothing here.
